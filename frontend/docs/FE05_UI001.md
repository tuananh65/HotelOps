## Contract bindings

Base: `/api/branches/{branchId}/inspection-checklists`.

| Operation              | Binding                                                                | Behavior                                                         |
| ---------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Open                   | GET `/{id}`                                                            | Read all versions and strong ETag from server                    |
| Create Draft           | POST base                                                              | code, name, description, roomTypeIds, criteria                   |
| Edit/create next Draft | PUT `/{id}`                                                            | criteria and reason only; original If-Match                      |
| Publish/Retire         | POST `/{id}/publish` or `/retire`                                      | reason, explicit confirmation, If-Match                          |
| RoomType selection     | GET `/api/room-types?branchId=...&isActive=true&page=...&pageSize=100` | Paginated active types in exact branch                           |
| CSRF                   | GET `/api/auth/csrf`                                                   | Fresh token per write; X-CSRF-TOKEN; cookie credentials included |

References: backend `InspectionChecklistsController`, `ChecklistDtos`, `Services/HotelStructure/ChecklistService.cs` (RoomTypeCreationService partial: ChecklistText/ValidateCriteria and checklist operations), `RoomTypesController`, and existing CSRF contract. No invented collection endpoint or permission code.

Use `/checklists?branchId=<real-id>` or `/checklists/<real-id>?branchId=<real-id>`. Branch and checklist identities must be actual positive safe integers; server enforces authorization/scope. Existing routes already mount the replaced screens. No mock identities, mock store, mock permissions, or synthetic checklist records are used by these two screens.

Historical criteria are displayed read-only. PUT changes criteria only, editing an unused Draft or requesting a new Draft through the existing service. Root name/code/applicability are never sent on update. Inspection-used Drafts cannot be edited or published. Published versions can be retired through the backend lifecycle. The UI does not grant permission: 401/403 clear loaded content and disable mutations; server permission remains authoritative. Stale/conflicting or uncertain write outcomes require reload/review rather than automatic retries.

## Integration gaps

1. The verified controller has NO checklist collection GET. The list is explicitly the records opened/created successfully from the server during this component session. A full branch catalogue needs an approved collection contract and owner delivery. No mock catalogue fallback exists.
2. RoomType GET requires MASTER_DATA_MANAGE while checklist writes require CHECKLIST_MANAGE. If unavailable, the form explains the limitation and allows known RoomType IDs; the backend checks validity/scope. A selector usable by checklist-only users needs an approved read contract/permission decision.
3. Shared frontend authentication/shell remains the existing prototype. These screens do not reuse its mock authority. A real backend cookie session and same-origin HTTPS API routing are deployment prerequisites; neither shared auth nor shared Vite/router configuration is changed here.
4. API requests use relative `/api` routes. The baseline Vite dev server has no real backend proxy; intercepted browser tests do not establish deployment transport or live authentication readiness.

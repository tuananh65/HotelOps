## Contract and behavior

`GET /api/branches/{branchId}/inspection-checklists?page=1&pageSize=20`

Uses existing feature transport: relative same-origin URL, cookie credentials, no-store, abort signal and existing error mapping. Collection GET does not request a CSRF token and requires no ETag. Optional parameters are `search`, `isActive`, `status`, `roomTypeId`. Blank filters are omitted; `isActive=false` is preserved. Search is trimmed, at most 200 characters without control characters; pagination is 1-based, pageSize 1..100, int32 overflow guarded. The UI offers 20/50/100 rows per page.

Response: `items,total,page,pageSize,branchId,isActive,search,status,roomTypeId`.
Each item: `id,branchId,code,name,active,roomTypeIds,versions`.
Each version summary: `id,number,status,effectiveAt,publishedBy,usedByInspection`.

The collection validator is separate from detail validation: no criteria or ETag is expected. Cross-branch/unsafe identity, malformed summaries and mismatched response pagination/filter echoes fail closed as an API-response error. No collection object is fed to a mutation or used as authorization.

- Lists all matching server records by page, replacing UI001's session-loaded record list. No mock store or synthetic checklist records are read.
- Search, active/status/RoomType filters apply through server query parameters. Applying or clearing filters resets to page 1. Filtering by status means ANY stored version, including history, and the table shows all returned version summaries. No synthetic current status is inferred.
- The UI renders loading, empty, error and pagination controls; manual reload preserves current applied filters/page. Empty out-of-range pages retain the server total and allow previous-page navigation.
- Superseded requests are aborted; responses are ignored after cancellation. Page data is cleared while loading/on errors instead of displaying it as current.
- Opening a collection item uses its ID to perform a fresh detail GET, including reopening the same item. Only detail response ETag is used for mutations. Direct existing detail routes remain supported.
- Successful Create, Update, Publish and Retire trigger a new collection GET with current applied filters/page. No optimistic insertion of mutation/detail response into the collection occurs. Records that no longer match filters disappear according to the refreshed server response.
- 401/403 clears/hides list records and closes active detail/create forms through the existing feature boundary; create is disabled until a successful read. Reload can recover after a valid session/permission is restored. Shared authentication is not implemented here.
- Existing historical protection, explicit Publish/Retire confirmation, stale write blocking and detail reload remain intact.

# UC-006 contract — HTTP NOT IMPLEMENTED

Approved candidate: PATCH `/api/users/{userId}/status`, body exactly `{ "status": "ACTIVE" | "INACTIVE", "reason": "..." }`. These are the SRS states of `User.AccountStatus`, not EmploymentStatus. Unknown/duplicate keys, wrong types/case, missing fields or trimmed reason shorter than 10 characters are rejected. Both operations require reason. No additional maximum reason length was found in the consulted UC-006/SRS input rules; audit JSON is mapped as nvarchar(max). A transport size limit must be reviewed before HTTP exposure, rather than inventing a business maximum.

Parser and service-level validation are implemented. Same-status and unknown-source transitions are rejected. Candidate HTTP mapping: invalid input400, unauthenticated401, forbidden403, invisible/missing/deleted404, no-op409, missing If-Match428, stale412, success200 with committed ETag and a small status DTO. 409 no-op is the explicitly approved fallback. Missing/malformed header handling and these HTTP mappings are NOT IMPLEMENTED or tested for UC-006; other workflows retain their existing contracts.

Future controller must resolve actor from authenticated SQL-backed session, accept no actor/branch/credential fields, use existing CSRF/authentication conventions, enforce no-store, and never return EF entities, credentials or session secrets. No status endpoint is exposed in this task. Activation service success contains only result status and committed rowversion. No plaintext credential is generated, stored, returned or replayed by activation.

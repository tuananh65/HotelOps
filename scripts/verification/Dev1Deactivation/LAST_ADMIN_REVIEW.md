# Last global-administration principal - NOT IMPLEMENTED / BLOCKED

Approved invariant: at least one ACTIVE, nondeleted, login-eligible principal retains simultaneously effective **unbound** USER_MANAGE/ALL and ROLE_MANAGE/ALL. Count principals, not roles/grants; independently valid grants can belong to different roles of the same principal. SYS_ADMIN/OWNER names are not evidence. Self-deactivation remains forbidden, but that alone cannot serialize two administrators removing each other's capability.

## Exact capability evidence

`Security/Authorization/PermissionService.cs` and `PermissionDataSource.cs` require active User, active assignment/role, AssignedAt <= server time, ExpiresAt absent/future, correct grant code and scope. Only assignment BranchId NULL with ALL grants global access without Branch context; Branch-bound ALL must not count. Membership/active Branch affect Branch-bound paths, not the unbound ALL predicate. The current PermissionService checks one validated request principal; it is not an administrator enumeration API. Do not synthesize another actor/session to reuse it for counting.

`AuthenticationLoginService.Candidates:88` resolves Username OR Email under SQL collation and refuses ambiguous candidates. `SqlSessionPolicy.IsUserActive:12` checks ACTIVE/nondeleted, not employment_status. CredentialLockoutService verifies the supported credential under a User lock and applies lock/temporary-expiry rules. `PasswordCredentialService.IsSupportedV3Hash` is private; nonempty password_hash alone does not prove supported login credentials. Actual password knowledge is not something a capability COUNT can verify.

Temporary-valid credentials allow restricted login, whereas PermissionService rejects restricted sessions for administration and AdminReauthenticationService requires a regular credential. Counting these as usable administrators needs an explicit reconciliation of the approved login-eligible/admin-capable invariant. No invented employment/hash or restricted-session rule is implemented here.

## Proposed shared protocol - design only, not approved integration

All capability-affecting writers need one common transaction-owned serialization boundary, for example a single SQL applock key agreed by both owners, acquired **before** User, role/catalog and feature locks. Under it: lock affected/candidate Users in ascending ID, lock eligible assignment/grant rows and relevant absent ranges, re-read latest capability plus login eligibility, apply proposed loss, and refuse if no qualifying principal remains. Retain locks/guard through audit and commit/rollback. A plain COUNT followed by UPDATE, or per-target User locks alone, is insufficient.

This protocol requires integration into every participating capability writer; adding a mutex only in Deactivate would not solve competing revoke/reset/lockout/identifier changes. Global-first ordering must be reviewed against UC-004's Branch/Department/Role-first locks and current auth user-first locks. Acquiring the global mutex late in an already User/resource-locked transaction risks inversion. Eligibility queries also need stable enumeration/range coverage; no candidate query/locking plan has been verified.

Required isolated SQL tests after contract and implementation: opposite admin deactivations; concurrent role/permission removal or rebind; simultaneous lockout/reset/identifier collision; expired/future/inactive paths; two grants on one vs multiple principals; branch-bound ALL excluded; rollback/audit failure; actual blocking IDs and both transaction orders. **NOT RUN** in Task 40. No UC-010 endpoint, global guard, count-and-update primitive or false PASS is introduced.

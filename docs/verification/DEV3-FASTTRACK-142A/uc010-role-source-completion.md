The existing assign/reactivate flow and the revoke confirmation now share the canonical role-management entry. Revoke is mounted in both frontend hosts and registered in the API. Read access does not authorize mutation. Both writers require a current unrestricted session, an active unbound SYS_ADMIN role and global USER_MANAGE plus ROLE_MANAGE. No role IDs or grants are fabricated.

Source acceptance mapping:

- Normal steps 1–3: account → Roles shows existing assignments and the active catalog; assignment/reactivation and explicit per-assignment revoke confirmation are connected to their APIs. Revoke uses the account ETag and fetches a CSRF token immediately before a single DELETE; unknown outcomes are never retried automatically.
- Steps 4–5: revocation owns a Serializable SQL transaction, the global administration lock, User/authority locks and current responsibility ranges. It validates identity, assignment, account state, rowversion, role/grant expiry and responsibility consistency before mutation and rechecks the staged state. Role deactivation, session invalidation and before/after audit commit together. Every early failure rolls back.
- Steps 6–7: effective grants are recomputed from SQL before/after and recorded in audit; all target sessions are invalidated. Confirmation returns the new ETag, and the UI links back to a fresh access review.
- Exception 4.1: the last durable Administrator must retain an actual active SYS_ADMIN role as well as both administration permissions. Expiry reporting includes actor-role expiry. Revoking one's own SYS_ADMIN assignment is rejected. A non-Administrator self-revocation still requires surviving administration authority; the initiating session is validated before intentionally invalidating target sessions.
- Exception 4.2 / MSG34: before/after capability checks cover task executors, cleaning/rework executors, inspectors, maintenance/preventive executors, IR handlers and pending handovers, shift handovers, workdays/future shifts, recurring-task responsibilities, designated Heads and pending material approvals/requester work. Actor eligibility is read independently from role permissions. Removing a permission or required actor role is blocked even if a different role carries similarly named permissions. Up to 200 dependent identifiers are returned only after global administrator authorization; they do not authorize access to work records.
- Approved UC140 dependency: SHIFT_HANDOVER_VIEW/SUBMIT/DECIDE are evaluated independently, with current branch, membership and receiver assignment checks. No automatic grant or assignee transfer.

Historical creator/reviewer/fulfiller attribution does not become a new execution responsibility. Department authority is not inferred from User.DepartmentId. Department Head designation prerequisites are preserved without rewriting mappings. Asset custody/warehouse manager remain active-account designations; a pending asset handover with unapproved production authorization, an unlinked legacy defect, missing installed workflow storage or inconsistent source data remains fail-closed. These cases need the appropriate workflow/data owner to resolve; no broad last-capable-worker policy is invented.

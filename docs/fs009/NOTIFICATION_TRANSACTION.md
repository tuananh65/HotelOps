# Notification transaction and physical boundary

One owner: existing BatchAsync, Serializable HotelOpsDbContext transaction. Order: sorted affected Users eligibility locks -> SQL session/current permission -> retained active Branch -> existing catalog app lock -> branch/task/current pointer/source checks -> actor/key operation range under UPDLOCK/HOLDLOCK -> assignment/task transition/audit -> EF operation/publication/intent staging -> final actor/session/grant gates and new-mutation assignee due/eligibility -> physical identity + SQL persisted guard -> outer CommitAsync. No second transaction owner, no separate Notification DbContext, no network delivery inside business transaction. This scoped order is not a proven global DEV2/DEV3 writer graph.

The SQL guard validates actual assignment ID, assigned actor/recipient/task/room/branch/logical cycle/time, publication operation/id/revision, durable result identity/tag and audit operation/assignment identity, plus exactly one recipient intent. Insert-time source trigger checks revision/deadline against persisted task at publication time. Publication/completed result become immutable. Replay can retain historical original result without requiring old task revision still current.

Before commit: audit/staging/constraint/guard exceptions cause disposal/rollback of whole operation. Real staging fault leaves assignment/task/audit/operation/publication/intent snapshots unchanged. Create has separate audit-fault total rollback proof. Same-context EF staging and guard use actual transaction connection; wrong physical transaction rejected.

After commit: explicit candidate delivery first claims in a short transaction, then separately writes existing notifications+notification_recipients+intent DELIVERED atomically. DB/source errors leave business committed and schedule durable retry. No reexecution of Assign to deliver. Claim identity/lease and rowversion prevent stale worker ownership; cancellation preserves lease for later recovery. Inbox insertion fault rolls back partial inbox and retains PENDING intent.

Limits: arbitrary external ADO commits are unsupported/unintercepted; physical commit response-loss exception injection, sync-commit bypass and global-writer race acceptance NOT_RUN. No complete C01 claim. Candidate is isolated and default-off; shared/production activation remains unavailable.

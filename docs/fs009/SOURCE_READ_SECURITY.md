# Source-read and recipient security

Recipient is persisted CleaningAssignment.AssigneeUserId, frozen into publication and unique intent. No department broadcast, ManagerUserId fallback or producer HttpContext in delivery. Actual current user account/employment/not-deleted, branch membership, active branch/source room and current CLEANING_VIEW grant paths evaluated independently. OWN requires exact ACTIVE/unended assignment belonging to that user; BRANCH/GLOBAL still require actual source lineage. Notification never grants source access or expands Monitor scope.

Delivery terminal policy: recipient missing/inactive/out-of-scope; source missing; exact assignment ended/nonactive SUPERSEDED; current source-read denied. Unrelated progress rowversion change does not supersede assignment: identity+responsibility govern, not latest task revision. Missing source/account FK states may be unreachable under normal constraints; code handles them but no nonexistent-row test is fabricated. Database/source exceptions propagate to retry, not a false permanent denial.

ReadCandidateCleaningInboxAsync exposes only delivered intents belonging to current session user and requested actual branch, checks CLEANING_VIEW current SQL paths then rechecks each exact source assignment before returning minimal own notification/action DTO. Existing source header route retained. Revoked permission hides already-delivered source actions; another assignee cannot see the recipient row. No shared inbox controller replaced.

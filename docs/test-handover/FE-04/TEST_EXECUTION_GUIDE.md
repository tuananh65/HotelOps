# Execution and defect workflow

1. Confirm branch/SHA, isolated DB owner/local identity, fixture time/shift and candidate flag. Read KNOWN_ISSUES. Do not use production accounts/data.
2. Start owned HTTPS environment per TEST_ENVIRONMENT. Login through UI with owner-provided synthetic credentials. For API tests GET /api/auth/csrf, POST /api/auth/login with X-CSRF-TOKEN, preserve cookie jar; obtain a fresh CSRF token for mutations. Never attach raw HAR/cookies/tokens/passwords to reports.
3. For each workbook row select a new unused room/task/key as instructed. Record actual numeric B1/task/assignment/publication identifiers privately or in sanitized test evidence; do not guess IDs.
4. UC028: GET /api/branches/{B}/cleaning-task-options?roomId={R}; POST /api/branches/{B}/cleaning-tasks with roomId, cleaningTypeId, priorityId, UTC dueAt and optional instruction. Expect 201/ETag; query current cycle, readiness event and audit in same source scope. Open detail/Monitor and refresh.
5. UC029: POST /api/branches/{B}/cleaning-tasks/{T}/assign with strong quoted 16-uppercase-hex If-Match, GUID Idempotency-Key, fresh CSRF; body assigneeId, UTC dueAt, reason, adoptUnassignedLegacy=false. Replay MUST preserve original body/key/If-Match. Do not replace original tag with current tag. Record 200/400/401/403/409/412/428/503 as specified, not merely any 2xx.
6. Observe SQL with read-only queries scoped by exact task/actor/operation/publication: cleaning_assignments, audit_logs, notification_operation_reservations, notification_publications and notification_delivery_intents. Compare baseline/delta and source revision/assignee/branch; inspect notification_recipients for delivery triple uniqueness. Request JSON contains source facts only for authorized recipients. Do not export whole user/credential/session tables.
7. For component/fault rows use exact guarded FS010 commands; stage/inbox/audit faults restore in finally. No ad hoc data repair is allowed to turn a failing result into PASS. For commit simulation distinguish test doubles/provider error injection from actual API/network failure. For raw-provider canary record UNSUPPORTED_BYPASS_CONFIRMED and C01 limitation, not complete acceptance.
8. In TESTER_TEST_CASES.xlsx fill Actual result, status PASS/FAIL/BLOCKED, evidence reference and Defect ID. Preserve existing expected results and IDs. Candidate-only cases do not certify accepted shared behavior. Shared publisher case stays BLOCKED until exact accepted source/integration exists.
9. Defect: record build SHA, case ID, environment/flag, minimal steps, expected/actual, sanitized HTTP status+body and before/after SQL counts, severity and reproduction frequency. Keep original failed full-run receipt separate from focused rerun.
10. Retest after developer fix using a new run ID; keep old failed evidence; rerun affected regression and one uninterrupted full suite. Never combine partial+focused reruns into a full PASS.
11. Return TESTER_ACCEPTANCE_REPORT using TESTER_FEEDBACK_TEMPLATE. Only Tester may grant TESTER_ACCEPTED; include explicit exclusions and blocked accepted integration cases. DEV_VERIFIED and package preparation are not Tester acceptance.
